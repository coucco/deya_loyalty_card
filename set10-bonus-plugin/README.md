# Плагин начисления бонусов для касс Set Retail 10 (ТРЦ «Дея», гипермаркет)

Java-плагин (jar) для касс Set Retail 10. После пробития чека передаёт данные чека и номер карты покупателя
на **сервер лояльности ТРЦ**. Сервер сам считает баллы (процент задаётся на сервере, в плагине процентов нет).

## Границы ответственности

| Что | Кто делает |
|---|---|
| Скидки на товары по карте («цена 3») | **Сервер Set10** (плагин скидок не даёт) |
| Определение карты на кассе (сканирование QR из приложения) | Касса Set10 |
| Передача пробитого чека и карты на наш сервер | **Этот плагин** |
| Подсчёт и начисление баллов, баланс, история, пуши | Наш сервер лояльности и приложение |

Плагин не меняет чек, ничего не показывает кассиру и не влияет на оплату. Любая ошибка внутри плагина
перехватывается и пишется в лог, пробитие чека она не блокирует.

## Как это работает

```
Покупатель показывает QR из приложения
   → касса (сканер) читает номер карты, Set10 считает свои скидки
   → чек оплачен и пробит (фискализирован)
   → плагин: POST на сервер лояльности (короткие таймауты)
        ├─ сервер ответил 2xx/409 → готово
        ├─ сервер ответил 400/404/410/422 → отказ, повторять не будем (запись в лог)
        └─ сервера нет / 5xx / 401 / 403 / 429 → чек уходит в очередь кассы,
           касса сама повторяет отправку (onSendFeedback); при повторе ключ тот же,
           поэтому баллы не начислятся дважды
```

Если сервер недоступен 3 раза подряд, плагин на 30 секунд перестаёт пытаться отправлять сразу
(чтобы кассир не ждал таймаутов), чеки в это время идут в очередь и уйдут позже.

## ВАЖНО: допущения (подтвердить до запуска)

1. **QR в приложении содержит номер карты, существующей в Set10.** Тогда касса сама находит карту, а
   плагин берёт номер из чека. Если в QR будет зашит свой одноразовый код приложения (меняющийся каждую минуту),
   его должен будет распознавать отдельный плагин карт (`CardPlugin`); сейчас он не входит в плагин.
   Как карты покупателей попадают в Set10 (выпуск заранее, загрузка с нашего сервера) — отдельный вопрос
   к проекту, см. «Открытые вопросы» в README проекта.
2. **Версия Set Retail 10 на кассах не подтверждена.** Плагин рассчитан на широкий диапазон версий
   (подробности ниже). В документации и SDK самые ранние версии касс, упоминаемые для плагинов, это ветка 10.2.x
   (например, 10.2.47 и 10.2.75). Если ваши кассы старше (например, версии 2012–2018 годов),
   плагины на них, скорее всего, не поддерживаются, и тогда нужно обновление Set10 либо другой способ интеграции.
   Точную версию посмотрите в Set10 и сообщите.
3. **Начисление от суммы чека** (`receipt.total`, уже с учётом скидок). Решение, от чего и что считать
   (исключения вроде алкоголя и табака, оплата бонусами), принимает сервер: в запросе есть позиции, оплаты и признак
   `accrueAllowed` по каждой позиции.
4. **Возвраты** отправляются на сервер (операция `REFUND` с данными исходного чека), чтобы сервер мог отменить
   начисленные баллы. Отключается настройкой `send.refunds`.

## Совместимость с версиями касс

* Реализован метод `eventReceiptFiscalized`. Он помечен устаревшим, но вызывается кассами всех версий:
  напрямую (старые) или через `onReceiptFiscalized` (с API 0.0.46, касса 10.2.71.0).
* Данные, которые есть только в новых версиях API (фискальный номер документа, данные смены — с API 0.0.73;
  признак разрешения начислений по позиции), читаются защищённо. Если их нет, плагин не падает:
  ключ чека строится запасным способом (касса + смена + номер чека + время создания).
* Без внешних библиотек: используется только стандартная Java 8 (`HttpURLConnection`). Так плагин не зависит
  от набора библиотек на кассе.
* `@PostConstruct` не используется (доступен только с кассы 10.2.47.0).

## Сборка

Нужны JDK 8 или новее и Gradle (интернет не требуется: единственная зависимость лежит в `libs/`).

1. Откройте `gradle.properties` и впишите **реальные контакты поставщика** (`vendorEmail` или `vendorPhone`):
   они обязательны в манифесте jar. В готовом `dist/*.jar` стоит заглушка `CHANGE_ME@example.com`.
2. `gradle build`: компилирует под Java 8, запускает самопроверку, собирает `build/libs/DeyaBonusAccrualPlugin.jar`.
3. Только проверки: `gradle selfTest`.

Если Gradle не установлен, можно взять wrapper из любого примера SDK либо собрать вручную:
`javac --release 8 -cp libs/*.jar:<slf4j-api.jar> -d out src/main/java/ru/deya/loyalty/*.java`,
затем упаковать `out`, `metainf.xml` и `strings_*.xml` в jar с манифестом (атрибуты см. `build.gradle`).

## Установка

Порядок основан на официальной статье «Установка и настройка плагина» (Confluence CSI) и чек-листе приёмки
из SDK. Для плагинов лояльности пошаговой статьи в открытом доступе нет: названия разделов меню сверьте со своей
версией Set10 или со службой поддержки CSI.

1. **Скопируйте `DeyaBonusAccrualPlugin.jar` вручную на все узлы**: сервер SetRetail (и SetCentrum, если он есть)
   и все кассы гипермаркета. Автоматической доставки файла плагина на кассы нет.
   * Сервер Linux: `/var/lib/jboss/plugins/`
   * Сервер Windows: `{диск}:\SetRetail10\plugins\`
   * Касса: `\storage\crystal-cash\plugins\`
2. **Зарегистрируйте и настройте плагин на сервере**: «Интеграция → Внешние процессинги». В списке появится
   «Начисление бонусов (ТРЦ Дея)». Заполните настройки:

   | Настройка | Что указать |
   |---|---|
   | Плагин включён | Аварийный выключатель (по умолчанию включён) |
   | Адрес сервера | Полный URL, например `https://loyalty.example.ru/api/v1/accruals` |
   | Ключ доступа | Ключ, который выдаёт ваш сервер лояльности |
   | Идентификатор точки | По умолчанию `hypermarket` |
   | Префиксы карт | Например `2000`; пусто = любая карта, кроме купонов и подарочных |
   | Таймаут соединения / ответа | По умолчанию 1500 / 3000 мс |
   | Отправлять возвраты | По умолчанию да |
   | Лимит повторов | По умолчанию 200 (сетевые сбои не считаются) |

3. **Проверьте порядок применения провайдеров лояльности**: плагин должен быть в списке. Скидок он не даёт,
   поэтому порядок на расчёт скидок Set10 не влияет.
4. Дождитесь, пока настройки **дойдут до кассы** (по транспорту Set10), и **перезапустите кассовый модуль**
   на каждой кассе.
5. HTTPS: сертификат сервера должен быть доверенным для Java на кассе. Старые версии Java 8 могут не знать
   новых корневых сертификатов (например, Let's Encrypt). Если запросы падают с ошибкой SSL, импортируйте
   нужный сертификат в хранилище Java кассы (или временно используйте внутренний адрес по HTTP в закрытой сети).

## Контракт API: что должен принять сервер

`POST <server.url>`, `Content-Type: application/json; charset=utf-8`

| Заголовок | Значение |
|---|---|
| `Authorization` | `Bearer <ключ доступа>` (если ключ задан) |
| `Idempotency-Key` | Ключ чека (то же, что `idempotencyKey` в теле) |
| `X-Point-Id` | Идентификатор точки |

**Ответы сервера и действия плагина**

| Ответ | Смысл | Плагин |
|---|---|---|
| `200`–`299` | Принято, баллы начислены | Готово |
| `409` | Этот чек уже обработан | Готово (баллы второй раз не начисляются) |
| `400`, `404`, `410`, `422` | Окончательный отказ (например, неизвестная карта) | Повтор не нужен, запись в лог |
| `401`, `403`, `429`, `5xx`, иное | Временная ошибка | Повтор позже (после исправления ключа дойдёт) |
| Нет связи | Сервер недоступен | Повтор позже, попытки не считаются |

**Сервер обязан быть идемпотентным по `idempotencyKey`:** повторный запрос с тем же ключом не должен начислять баллы
второй раз (ответ `409` или `200` с прежним результатом).

**Тело запроса** (реальный пример, сформированный плагином):

```json
{
  "schemaVersion": 1,
  "idempotencyKey": "fd:9999078900001234:777",
  "pointId": "hypermarket",
  "registerId": "9999078900001234",
  "operation": "SALE",
  "card": { "number": "2000000000017", "type": "INTERNAL" },
  "receipt": {
    "key": "fd:9999078900001234:777",
    "registerId": "9999078900001234",
    "number": 42,
    "shiftNo": 5,
    "fiscalDocId": 777,
    "fiscalSign": 123456789,
    "fiscalizedAt": "2025-10-09T11:55:00+03:00",
    "createdAt": "2025-10-09T11:53:20+03:00",
    "total": "1234.50",
    "fnNumber": "9999078900001234",
    "registerFactoryNumber": "0012345678"
  },
  "payments": [ { "type": "cash", "sum": "1234.50", "annulling": false } ],
  "lines": [
    { "number": 1, "name": "Молоко \"Дея\" 1л", "barcode": "4600000000011", "marking": null,
      "groupCode": "G1", "quantity": "1.500", "price": "100.00", "sum": "150.00",
      "discount": "0.00", "accrueAllowed": true }
  ]
}
```

Пояснения:
* Суммы и количества, передаваемые строками, не теряют точность (`"1234.50"`, `"1.500"`).
* `operation`: `SALE` или `REFUND`. При `REFUND` добавляется блок `originalReceipt` (того же вида, что `receipt`),
  по нему сервер находит исходное начисление. Если карту в возврате не прикладывали, она берётся из исходного чека.
* `idempotencyKey`: `fd:<номер ФН>:<номер ФД>` (если касса отдаёт эти данные), иначе
  `rc:<касса>:<смена>:<номер чека>:<время создания>`. Сервер должен уметь связать возврат с исходным чеком
  по `originalReceipt.key`; на старых кассах без фискальных данных дополнительно сопоставляйте
  по смене, номеру чека и времени создания.
* Личные данные покупателя (ФИО, телефон) плагин не передаёт: только номер карты. Номер карты в логах кассы
  маскируется (последние 4 цифры).
* `fnNumber`, `fiscalDocId`, `fiscalSign`, `registerFactoryNumber`, `fiscalizedAt`, `payments` на старых кассах
  могут отсутствовать (`null` или поле опущено).

## Проверка

### 1. До кассы (на вашем компьютере)

`gradle build` запускает самопроверку: разбор чека, фильтры карт, старые версии API, возвраты, ответы сервера
(2xx, 409, 422, 404, 500, 401, нет связи), очередь и повторы, лимит попыток, предохранитель. Результат:
`Проверок выполнено: 54, ошибок: 0`.

### 2. Сервер-имитация (до готового сервера лояльности)

```
python3 tools/mock_server.py --port 8080 --percent 5 --api-key secret
```

Он ведёт себя как будущий сервер: проверяет ключ, считает баллы, на повтор чека отвечает `409`, пишет принятые чеки
в `accruals.jsonl`. Для проверки очереди кассы: `--fail-first 3` (первые 3 запроса отвечают 500) и `--delay 5`
(проверка таймаутов). Адрес в настройках плагина: `http://<ваш компьютер>:8080/api/v1/accruals`.

### 3. На тестовой кассе Set10 (обязательно до гипермаркета)

Не ставьте плагин сразу на боевые кассы: Set10 предупреждает, что непрошедшие проверку плагины ограничивают
работу кассы. Нужна тестовая касса (или тестовый магазин) с тестовой картой в Set10.

| № | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | Плагин положен на сервер, зарегистрирован | В «Внешних процессингах» есть «Начисление бонусов», поля настроек совпадают с `metainf.xml` |
| 2 | Настройки сохранены | Дошли до кассы, касса перезапущена, в логе кассы нет ошибок загрузки плагина |
| 3 | Тестовая карта добавлена в чек (сканером QR), чек оплачен наличными | Чек пробит; на сервере-имитации появилась запись с номером карты и суммой |
| 4 | Сервер-имитация запущен с `--delay 5 --delay-first 1` (первый ответ приходит позже таймаута 3 с), пробит чек | Плагин не дождался ответа и поставил чек в очередь; сервер всё же записал его. Повтор из очереди получил `409`, второго начисления нет |
| 5 | Сервер выключен, пробит чек | Чек пробит без задержек и ошибок для кассира; запись осталась в очереди |
| 6 | Сервер включён | Чек из очереди доходит сам (касса повторяет отправку периодически, засеките время и запишите), начисление одно |
| 7 | Сервер отвечает `500` (`--fail-first`) | Повторы идут; после 200 чек доставлен |
| 8 | Неверный ключ доступа | В логе кассы ответ `401`, чек остаётся в очереди; после исправления ключа доходит |
| 9 | Чек без карты | Запросов на сервер нет |
| 10 | Чек с другой картой/купоном | Не отправляется (если задан префикс) |
| 11 | Возврат по чеку продажи | Приходит `REFUND` с `originalReceipt` |
| 12 | Скидки Set10 по карте («цена 3») | Применяются как раньше; плагин на них не влияет |
| 13 | Выключатель «Плагин включён» снят | Запросов нет, касса работает как обычно |

Логи плагина смотрите в логах кассы (плагин пишет только через внедрённый логгер). Номера карт в логах
замаскированы, ключ идемпотентности виден целиком.

### 4. Приёмка CSI

В SDK есть «Чеклист приёмки плагина лояльности» (`checklists/Loyalty_and_cards_checklist.pdf`): CSI просит исходный
код, описание сценариев использования, эмулятор процессинга (подойдёт `tools/mock_server.py`),
проверку `metainf.xml` утилитой `utils/MetainfValidator.jar` (требует Java 8; здесь манифест проверен по той же схеме
`metainf.xsd`) и обязательные атрибуты манифеста jar. Подробнее про сертификацию уточните в CSI до запуска на боевых кассах.

## Ограничения версии 1.0

* Нет немедленного ответа на кассе («начислено N баллов»): сервер считает баллы асинхронно, покупатель видит результат
  в приложении. Печать начисленных баллов на чеке при необходимости можно добавить (API поддерживает слипы).
* Нет распознавания собственных QR-кодов приложения (см. допущение 1).
* Начисление не от оплаты бонусами/суммы без скидок: расчёт полностью на сервере по полям запроса.
* Тестировался на поддельных данных чека и локальном сервере; на настоящей кассе Set10 плагин ещё не запускался.
