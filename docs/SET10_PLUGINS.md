# Плагины Set10: какие методы где вызываются и что нам нужно

Источники: исходники Set API в `set10-bonus-plugin/libs/set10pos-api-…jar` (javadoc интерфейсов) и статьи Crystals «API Set10 ◾ Описание плагинов», «◾ Плагин лояльности», «◾ Плагин-считыватель» (PDF от 17.10.2026). Порядок вызовов внутри одного этапа подтверждаем логами на тестовой кассе (`log.payload`, см. `TEST_PLAN.md`).

Что из документации Crystals повлияло на код:
* **Номер чека на расчёте скидок может отличаться от номера при фискализации** (если между ними печатались X-отчёт, копия чека). Поэтому ссылка на чек для резерва/списания баллов (`ref`) строится без номера: касса + смена + время создания чека, а при фискализации берётся из нашего же результата расчёта.
* После фискализации скидки могут быть **перераспределены по 54-ФЗ** (в т.ч. разбиение позиций) — списание сервер подтверждает по сумме баллов, а не по позициям.
* **Плагин лояльности не может показывать формы кассиру** (uiForms) — диалоги активации карты делает плагин карт.
* **Скидка бонусами «в два расчёта»**: 1-й `doDiscount` отдаёт потолок списания, кассир вводит сумму, 2-й `doDiscount` превращает её в скидку. Баланс бонусного счёта кассе даёт **плагин карт**.

## 1. Этапы чека и методы плагинов

| Этап (по вашей схеме) | Что делает касса | Методы плагинов (интерфейс.метод) | Наш плагин |
|---|---|---|---|
| **Продажа** (добавление товаров и карт) | Сканирование ШК/QR, прокатка карты, ввод номера | `GoodsPlugin.findByBarcode/addForSale` (свои товары); `CardPlugin.searchCard` (карта **внешнего** процессинга); `BarcodeTransformerPlugin.transform`; `ExciseValidationPlugin.*`; `ReaderPlugin.start`; `FunctionPlugin.execute` (кнопка/WebView); `TechProcessPlugin.intercept` на `PRODUCT_FOUND_FOR_SALE`, `BEFORE_POSITION_ADD` | — (карту Set10 узнаёт сама) |
| **Расчёт скидок** (подытог) | Касса считает свои акции (в т.ч. «цену 3»), затем плагины лояльности **по порядку провайдеров** | `TechProcessPlugin.intercept(SUBTOTAL_START)` → `LoyaltyPlugin.onDiscountCalculationStarted` (API 0.0.70+) → `AdvertisingActionProviderPlugin.getAdvertisingActions`, `AdvertisingActionConditionPlugin.isConditionExecuted` → **`LoyaltyPlugin.doDiscount`** (получает чек «с уже данными скидками других поставщиков») → `LoyaltyPlugin.onDiscountCalculationFinished` (0.0.39+, корректировка лимитов) → `TechProcessPlugin.intercept(CALCULATION_COMPLETE)` | `doDiscount`: списание баллов скидкой (если `redeem.enabled`) |
| Отмена расчёта (назад к товарам, аннулирование) | | **`LoyaltyPlugin.cancelDiscount`** (0.0.26+); `TechProcessPlugin` `DISCOUNT_CANCELLED`, `SUBTOTAL_CANCELED` | снимает резерв баллов |
| **Оплата** | Выбор способа, проведение | `PaymentPlugin.doPayment / doPaymentCancel`; `CardPlugin.writeOff/writeOffAsync` (списание бонусов карты внешнего процессинга кнопкой «оплатить бонусами») | — |
| **Предфискализация** | Чек готов к печати | `LoyaltyPlugin.eventBeforeReceiptFiscalized` (может вернуть слипы, начисления для печати); `TechProcessPlugin.intercept(BEFORE_FISCALIZE)` | — (здесь можно печатать «начислено N баллов», см. «Идеи») |
| **Фискализация** | ФН/ОФД | — | — |
| **Постфискализация** | Чек пробит | **`LoyaltyPlugin.onReceiptFiscalized`** (API 0.0.46+, по умолчанию вызывает устаревший `eventReceiptFiscalized`); `FiscalizationListener.eventReceiptFiscalized` (его наследуют `GoodsPlugin`, `PaymentPlugin`, `ExciseValidationPlugin`); `TechProcessPlugin.intercept(AFTER_FISCALIZE)` | отправка чека на сервер (начисление + подтверждение списания) |
| Фон, периодически | Очередь неотправленного | **`LoyaltyPlugin.onSendFeedback(Collection)`** (0.0.46+, по умолчанию вызывает `onSendFeedback(одно сообщение)`); `FiscalizationListener.onRepeatSend` | повтор отправки при сбое связи |
| Возврат | | `RefundPreparationPlugin`, `PaymentPlugin.doRefund`, `TransactionalRefundPlugin`; чек возврата тоже фискализируется → `onReceiptFiscalized` с `ReceiptType.REFUND` | отправка возврата (баллы отменяются, списанные — возвращаются) |

Важное из javadoc, влияющее на нас:
* `doDiscount` получает чек **со скидками, уже данными другими поставщиками** → наш плагин должен стоять **последним** в «порядке применения провайдеров лояльности», тогда «цена 3» уже видна в позициях.
* `onReceiptFiscalized`/`eventReceiptFiscalized` получают `LoyaltyResult` — то, что **наш** плагин дал в этом чеке; по нему мы сообщаем серверу фактическое списание.
* `onSendFeedback`: вернуть `null` = больше не повторять; вернуть тот же объект = повторить позже (касса хранит очередь сама, переживает перезапуск).
* В `CardPlugin.writeOff` нельзя показывать UI; в `writeOffAsync`, `cardSearchFinished`, `TechProcessPlugin.intercept` — можно.

## 2. Какие плагины в нашем jar и зачем

В одном `DeyaBonusAccrualPlugin.jar` (версия 1.2.0) два плагина с общими настройками (один «внешний процессинг» в Set10):

| Плагин | id | Что делает |
|---|---|---|
| `LoyaltyPlugin` — `BonusAccrualPlugin` | `ext.deya.bonus.accrual` | начисление по пробитому чеку и возвраты (очередь кассы при сбоях); списание баллов скидкой на подытоге (`redeem.enabled`, `redeem.mode`) |
| `CardPlugin` — `DeyaCardPlugin` | `ext.deya.card` | активация пластика на кассе (телефон + СМС-код); поиск клиента по телефону; «Инфо по карте» (профиль, баланс); в режиме `external` — баланс на экране кассира, кнопка «оплатить бонусами» (`writeOff`/`rollback`) |

| Задача | Чем решается |
|---|---|
| Карта опознаётся на кассе (QR, штрихкод, ввод номера, магнитная полоса) | номера заведены в Set10 как внутренние карты — штатно Set10; в режиме `external` — наш плагин карт |
| «Цена 3» по карте | акция Set10 на тип карты (цены из 1С) |
| Начисление, возвраты, повтор при сбое связи | `LoyaltyPlugin` |
| Активация пластика при первом использовании, на кассе | `CardPlugin.cardSearchFinished` — вызывается для **любой** найденной карты, в т.ч. внутренней карты Set10, поэтому работает в обоих режимах |
| Поиск по телефону | `CardPlugin.searchCardAsync` (источник PHONE_NUMBER) |
| Баланс у кассира | «Инфо по карте» (`getCardInfo`) — оба режима; на экране карты — только `external` |
| Списание автоматически (клиент включил в приложении) | `LoyaltyPlugin.doDiscount`, `redeem.mode=auto/both` |
| Списание по кнопке кассира «оплатить бонусами» | `CardPlugin` (`external`) + `LoyaltyPlugin` (потолок → скидка BONUSES) + `writeOff`, `redeem.mode=cashier/both` |

### Главный вопрос теста: режим карт `internal` или `external`

| | `card.mode=internal` (по умолчанию) | `card.mode=external` |
|---|---|---|
| Кто «владеет» картой на кассе | Set10 (внутренняя карта) | наш плагин карт (внешняя карта, `CardType.EXTERNAL`) |
| «Цена 3» по типу карты | ✅ штатно | ❓ **проверить** (этап 2b плана): Set10 может не применять акцию типа внутренней карты к внешней. Варианты: акция Set10 на **категорию** карты (плагин задаёт `card.category.guid`) или настройка поиска «сначала внутренние карты» |
| Баланс на экране, кнопка «оплатить бонусами» | ❌ (баланс — через «Инфо по карте») | ✅ |
| Активация, поиск по телефону, инфо по карте | ✅ | ✅ |
| Списание | автоматическое (по переключателю клиента) | автоматическое и/или кнопкой кассира |
| Без связи с сервером | карта работает как обычная | карта добавляется без баланса, «цена 3» и отложенное начисление работают |

Порядок: тестируем `internal` (этапы 1–5), затем переключаем `external` и проверяем «цену 3» (2b). Если «цена 3» работает — оставляем `external` (кнопка кассира + автосписание), если нет и не настраивается категорией — остаёмся в `internal` с автосписанием.

### Остальные плагины Set10: для чего они вообще

| Плагин | Назначение | Нам |
|---|---|---|
| `GoodsPlugin` | продажа «своих» товаров (сертификаты, услуги) | нет |
| `PaymentPlugin` | свой способ оплаты. Оплата баллами **как оплата** (а не скидка) усложняет 54-ФЗ; скидка — стандарт | нет |
| `TechProcessPlugin` | вклиниться в техпроцесс с диалогом кассиру | резерв: диалог «Списать баллы?» на `CALCULATION_COMPLETE` |
| `AdvertisingActionProvider/ConditionPlugin` | акции из внешней системы / свои условия акций | нет (цена 3 — штатная акция); позже — персональные акции из CRM |
| `FunctionPlugin` | кнопка в меню кассы, WebView | возможно позже: регистрация клиента на кассе |
| `ReaderPlugin` | приём товаров из внешних систем (пик-листы, планшет) | нет |
| `BarcodeTransformerPlugin`, `ExciseValidationPlugin`, `AgeConfirmationPlugin` | ШК, маркировка, возраст | нет |

## 3. Списание в гипермаркете и «цена 3»

```
подытог:  Set10 считает «цену 3» → наш doDiscount (ПОСЛЕДНИЙ в порядке провайдеров лояльности)
  auto:    сервер: база = позиции, где payBonusAllowed и нет скидки Set10 («цена 3», настраивается);
           лимит = база × «Макс. оплата баллами, %» точки «Гипермаркет» (5 %); только если клиент включил в приложении
           → резерв, скидка по позициям, кассиру «Оплата баллами: N б.»
  cashier: 1-й расчёт → потолок (writeOffsLimits); кассир «оплатить бонусами», вводит сумму;
           2-й расчёт → скидка BONUSES на эту сумму; CardPlugin.writeOff → баллы списаны (откат — rollback)
пробит:    onReceiptFiscalized → начисление (от суммы после всех скидок) + подтверждение списания
отмена:    cancelDiscount → резерв снят (без связи — истечёт сам через POS_HOLD_TTL_SEC)
```

* Лимит списания, исключения и курс задаёт **сервер** (админка): «Макс. оплата баллами, %», «разрешать оплату баллами товаров со скидкой Set10», список id акций «цены 3». Плагин чисел не знает.
* Как сервер узнаёт «цену 3»: плагин передаёт по позиции `discount` и применённые акции `discounts[{id, guid}]`. Если Set10 делает «цену 3» подменой цены, а не скидкой — исключаем флагом Set10 «запрет оплаты бонусами» на товарах (`isPayBonusAllowed=false`).
* Кнопка кассира не требует переключателя в приложении (клиент просит сам у кассы), но карта должна быть привязана к телефону.

## 4. Профиль, виртуальная и пластиковая карты

**Баллы принадлежат профилю, а не карте.** Профиль — один на телефон, у него неизменный **ID профиля** (7 цифр, например `1000007`): по нему клиента находит поддержка, он печатается в «Инфо по карте». Телефон профиля можно сменить, ID — никогда. К профилю привязаны не больше одной виртуальной карты (QR в приложении) и одной пластиковой; номера из разных диапазонов. На кассе обе карты — карты Set10 с «ценой 3»; вход в приложение — по телефону профиля, баланс общий.

| Сценарий | Что происходит |
|---|---|
| Только приложение | регистрация по телефону → профиль + виртуальная карта (QR/штрихкод) |
| Только пластик, без телефона | покупки копят баллы на **гостевом профиле** карты (у него уже есть ID); списывать нельзя |
| Пластик → активация на кассе | кассир видит «Карта не активирована» → телефон покупателя → СМС с кодом → код → гостевой профиль становится профилем телефона (ID сохраняется), баллы на месте. Нет смартфона/интернета — не нужно |
| Пластик → активация в приложении | Профиль → «Привязать пластиковую карту», номер + код активации с обратной стороны |
| Активировали пластик, а по этому телефону уже есть профиль (приложение) | баллы карты переходят в существующий профиль; если у профиля уже был пластик — старый блокируется (замена) |
| Приложение после активации на кассе | вход по тому же телефону → тот же профиль и баллы, выдаётся виртуальная карта |
| Потеря карты | новую карту активируют на кассе или в приложении → старая блокируется автоматически; либо поддержка блокирует |
| Смена номера телефона | клиент: Профиль → «Сменить» → код на новый номер (профиль, баллы, карты те же). Нет доступа к старому номеру — поддержка меняет номер после проверки личности, все входы по старому номеру завершаются |
| Новый номер уже занят другим профилем | только поддержка: «Присоединить профиль» (баллы и карты переходят, правило 1+1, второй профиль закрывается) |
| Ошибочная привязка пластика | поддержка: «Отвязать» (баллы остаются в профиле, карта снова свободна) |
| Удаление аккаунта | виртуальная карта закрывается навсегда; пластик снова свободен (новый гостевой профиль при следующей покупке) |
| Обе карты в одном чеке | берётся первая — начисление одно |

**QR и штрихкод не меняются ежедневно**: в них номер карты Set10 (меняющийся код касса не узнает без перевода карт в `external`). Защита — привязка к телефону, списание только с привязанных карт, на 3 этаже — код подтверждения из приложения.

### Магнитная полоса и печать пластика

| Что | Решение |
|---|---|
| На полосе | только номер карты: дорожка 2 `;<номер>?` (ISO 7813); шифровать нечего (полоса копируется любым ридером) |
| Напечатать | номер цифрами, штрихкод Code128 с тем же номером (хватит обычного сканера), на обороте код активации (лучше под скретч-слоем) |
| Как читает касса | штатно Set10, как штрихкод; плагин карт тоже понимает дорожки 1 и 2 |

## 5. 3 этаж (кино, боулинг, другие кассы)

Без интеграции с их ПО: планшет/ПК с `/cashier` + USB-сканер QR/штрихкодов + при необходимости USB-считыватель полосы (оба работают как клавиатура; страница сама вырезает номер из `;номер=…?`). Подтверждение списания — 4-значный код в приложении клиента (без затрат на СМС). Интеграция с их ПО — позже через те же `/api/v1/redeem/*`.

## 6. Журнал, поддержка, резервные копии

* **Журнал действий**: каждый изменяющий запрос (клиент, касса, кассир, админ) и каждый просмотр админки — кто, что, откуда, результат; тела запросов (ПДн) не пишутся. Плюс бизнес-события (активация карты, смена номера, слияние, корректировки). Журнал баллов и согласий защищён от изменения триггерами БД. Хранение журнала действий — `AUDIT_KEEP_DAYS` (3 года).
* **Поддержка**: +7 929 838-45-16, timurshokarov1001@gmail.com (в приложении, письмо сразу с ID профиля). Админка → «Клиенты» → поиск по телефону/карте/ID → карточка клиента: карты, баллы, согласия, журнал; действия: смена телефона, присоединить профиль, заблокировать/отвязать карту, корректировка баллов — всё с причиной в журнале.
* **Резервные копии**: сервер сам делает ежедневную горячую копию (`BACKUP_DIR`, проверка целостности, хранение `BACKUP_KEEP_DAYS`), её нужно дополнительно увозить с сервера (см. `DEPLOY.md`).
