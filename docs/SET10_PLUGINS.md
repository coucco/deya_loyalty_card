# Плагины Set10: какие методы где вызываются и что нам нужно

Источник — исходники Set API, которые лежат прямо в `set10-bonus-plugin/libs/set10pos-api-…jar` (javadoc интерфейсов). Confluence Crystals из среды разработки был недоступен, поэтому **порядок вызовов внутри одного этапа подтверждаем логами на тестовой кассе** (настройка плагина `log.payload`, см. `TEST_PLAN.md`).

## 1. Этапы чека и методы плагинов

| Этап (по вашей схеме) | Что делает касса | Методы плагинов (интерфейс.метод) | Наш плагин |
|---|---|---|---|
| **Продажа** (добавление товаров и карт) | Сканирование ШК/QR, прокатка карты, ввод номера | `GoodsPlugin.findByBarcode/addForSale` (свои товары); `CardPlugin.searchCard` (карта **внешнего** процессинга); `BarcodeTransformerPlugin.transform`; `ExciseValidationPlugin.*`; `ReaderPlugin.start`; `FunctionPlugin.execute` (кнопка/WebView); `TechProcessPlugin.intercept` на `PRODUCT_FOUND_FOR_SALE`, `BEFORE_POSITION_ADD` | — (карту Set10 узнаёт сама) |
| **Расчёт скидок** (подытог) | Касса считает свои акции (в т.ч. «цену 3»), затем плагины лояльности **по порядку провайдеров** | `TechProcessPlugin.intercept(SUBTOTAL_START)` → `LoyaltyPlugin.onDiscountCalculationStarted` (API 0.0.70+) → `AdvertisingActionProviderPlugin.getAdvertisingActions`, `AdvertisingActionConditionPlugin.isConditionExecuted` → **`LoyaltyPlugin.doDiscount`** (получает чек «с уже данными скидками других поставщиков») → `LoyaltyPlugin.onDiscountCalculationFinished` (0.0.39+, корректировка лимитов) → `TechProcessPlugin.intercept(CALCULATION_COMPLETE)` | `doDiscount`: списание баллов скидкой (если `redeem.enabled`) |
| Отмена расчёта (назад к товарам, аннулирование) | | **`LoyaltyPlugin.cancelDiscount`** (0.0.26+); `TechProcessPlugin` `DISCOUNT_CANCELLED`, `SUBTOTAL_CANCELED` | снимает резерв баллов |
| **Оплата** | Выбор способа, проведение | `PaymentPlugin.doPayment / doPaymentCancel`; `CardPlugin.writeOff/writeOffAsync` (списание бонусов карты внешнего процессинга кнопкой «оплатить бонусами») | — |
| **Предфискализация** | Чек готов к печати | `LoyaltyPlugin.eventBeforeReceiptFiscalized` (может вернуть слипы, начисления для печати); `TechProcessPlugin.intercept(BEFORE_FISCALIZE)` | — (здесь можно печатать «начислено N баллов», см. «Идеи») |
| **Фискализация** | ФН/ОФД | — | — |
| **Постфискализация** | Чек пробит | **`LoyaltyPlugin.onReceiptFiscalized`** (API 0.0.46+, по умолчанию вызывает устаревший `eventReceiptFiscalized`); `FiscalizationListener.eventReceiptFiscalized` (его наследуют `GoodsPlugin`, `PaymentPlugin`, `ExciseValidationPlugin`); `TechProcessPlugin.intercept(AFTER_FISCALIZE)` | отправка чека на сервер (начисление + подтверждение списания) |
| Фон, периодически | Очередь неотправленного | **`LoyaltyPlugin.onSendFeedback(Collection)`** (0.0.46+, по умолчанию вызывает `onSendFeedback(одно сообщение)`); `FiscalizationListener.onRepeatSend` | повтор отправки при сбое связи |
| Возврат | | `RefundPreparationPlugin`, `PaymentPlugin.doRefund`, `TransactionalRefundPlugin`; чек возврата тоже фискализируется → `onReceiptFiscalized` с `ReceiptType.REFUND` | отправка возврата (баллы отменяются, списанные — возвращаются) |

Важное из javadoc, влияющее на нас:
* `doDiscount` получает чек **со скидками, уже данными другими поставщиками** → наш плагин должен стоять **последним** в «порядке применения провайдеров лояльности», тогда «цена 3» уже видна в позициях.
* `onReceiptFiscalized`/`eventReceiptFiscalized` получают `LoyaltyResult` — то, что **наш** плагин дал в этом чеке; по нему мы сообщаем серверу фактическое списание.
* `onSendFeedback`: вернуть `null` = больше не повторять; вернуть тот же объект = повторить позже (касса хранит очередь сама, переживает перезапуск).
* В `CardPlugin.writeOff` нельзя показывать UI; в `writeOffAsync`, `cardSearchFinished`, `TechProcessPlugin.intercept` — можно.

## 2. Какие плагины нужны нам (минимальный набор)

**Нужен один плагин: `LoyaltyPlugin` (наш `DeyaBonusAccrualPlugin.jar`).** Всё остальное делает штатный Set10.

| Задача | Чем решается | Плагин нужен? |
|---|---|---|
| Карта клиента опознаётся на кассе (QR из приложения, штрихкод, ручной ввод, магнитная полоса) | Номера карт **заранее заведены в Set10** как внутренние карты нужного типа; касса узнаёт их штатно (штрихкод/QR = номер, полоса = номер на дорожке) | **Нет** (CardPlugin не нужен) |
| «Цена 3» по карте | Акция/тип карты в Set10, цены из 1С | **Нет** (настройка Set10) |
| Начисление баллов за чек | `LoyaltyPlugin.onReceiptFiscalized` → наш сервер | **Да** |
| Повтор при отсутствии связи | Очередь кассы через `onSendFeedback` | входит в наш плагин |
| Списание баллов в гипермаркете (до 5 % и др. лимиты из админки) | `LoyaltyPlugin.doDiscount` — скидка, размер которой считает наш сервер | входит в наш плагин (выключено по умолчанию) |
| Возвраты | `onReceiptFiscalized` с `REFUND` | входит в наш плагин |

### Когда понадобился бы CardPlugin (и почему сейчас — нет)

| Сценарий | Без CardPlugin | С CardPlugin |
|---|---|---|
| Карты заведены в Set10 (ваш случай: пул из 10 тестовых, потом диапазоны) | ✅ работает | не нужен |
| Номера карт придумывает наш сервер и в Set10 их нет | ❌ касса не узнает карту | `searchCard` отвечает «это наша карта» |
| Динамический (одноразовый) QR против передачи карты | ❌ | ✅ |
| Поиск клиента на кассе по номеру телефона | ❌ | `searchCardAsync(PHONE_NUMBER)` |
| Баланс баллов на экране кассира, кнопка «Оплатить бонусами» штатным UI Set10 | ❌ (у нас: сообщение кассиру «Оплата баллами: N б.» после подытога) | `CardEntity` с балансом + `writeOff` |
| Привязка телефона к пластиковой карте прямо на кассе (форма ввода) | ❌ (у нас: привязка в приложении) | `cardSearchFinished` + UIForms |
| Чтение магнитной полосы | ✅ штатно, если на полосе номер карты | нужен, только если на полосе зашифрованные данные |

Вывод: CardPlugin добавим, только если бизнес захочет поиск по телефону на кассе или кнопку «оплатить бонусами» со штатным UI. Архитектура это допускает: сервер уже умеет `quote/hold/commit/cancel`.

### Остальные плагины: для чего они вообще

| Плагин | Назначение | Нам |
|---|---|---|
| `GoodsPlugin` | продажа «своих» товаров (подарочные сертификаты, услуги) | нет |
| `PaymentPlugin` | свой способ оплаты (банк, SBP, подарочная карта). Оплата баллами **как оплата** (а не скидка) усложняет 54-ФЗ: в чеке это «встречное предоставление»; скидка проще и стандартна | нет |
| `TechProcessPlugin` | вклиниться в техпроцесс с диалогом кассиру (например, «Списать 120 баллов? Да/Нет» на `CALCULATION_COMPLETE`) | возможное развитие вместо переключателя «Списывать баллы» в приложении |
| `AdvertisingActionProvider/ConditionPlugin` | акции из внешней системы / свои условия акций Set10 | нет (цена 3 — штатная акция) |
| `FunctionPlugin` | кнопка в меню кассы, WebView | возможное развитие (регистрация клиента на кассе) |
| `BarcodeTransformerPlugin`, `ReaderPlugin`, `ExciseValidationPlugin`, `AgeConfirmationPlugin` | преобразование ШК, внешние считыватели, маркировка, возраст | нет |

## 3. Списание в гипермаркете и «цена 3»: кто за что отвечает

```
подытог:  Set10 считает «цену 3» по карте  →  наш doDiscount (последний в порядке провайдеров)
          → сервер: база = позиции, где isPayBonusAllowed=true и НЕТ скидки Set10 (настройка «разрешать на цену 3» выкл.)
                    лимит = база × «Макс. оплата баллами, %» точки «Гипермаркет» (админка, напр. 5 %)
                    баллы = min(лимит, доступно), только если клиент включил «Списывать баллы в гипермаркете»
          → резерв баллов на сервере, скидка разложена по позициям → касса показывает кассиру «Оплата баллами: N б.»
чек пробит: onReceiptFiscalized → начисление (от суммы ПОСЛЕ всех скидок) + подтверждение списания одной транзакцией
отмена:     cancelDiscount → резерв снят (если связи нет — резерв истечёт сам через POS_HOLD_TTL_SEC)
```

* **Компонент, отвечающий за лимит списания, — наш сервер** (админка: «Макс. оплата баллами, % чека» у точки «Гипермаркет»; галочка «разрешать оплату баллами товаров со скидкой Set10»; список id акций «цены 3», если нужно отличать её от прочих скидок). Плагин чисел не знает.
* Товары с «ценой 3» по умолчанию **исключены из базы списания** (двойная выгода), но **участвуют в начислении** (настраивается: «начислять баллы на товары со скидкой Set10»).
* Как сервер узнаёт «цену 3»: плагин передаёт по позиции `discount` (скидка Set10) и список применённых акций `discounts[{id, guid}]`. Если в админке задан список акций «цены 3» — исключаются только они, иначе любая скидка Set10. **Проверить на тестовой кассе**: если Set10 реализует «цену 3» подменой цены, а не скидкой, позиции придут без скидки — тогда используем флаг Set10 «запрет оплаты бонусами» на этих товарах (`isPayBonusAllowed=false`), его плагин тоже передаёт.
* Согласие клиента: списание автоматическое, только если клиент включил переключатель в профиле. Это и есть «подтверждение» без UI на кассе. Альтернатива на будущее — `TechProcessPlugin` с вопросом кассиру.

## 4. Пластиковые карты с магнитной полосой

| Вопрос | Решение |
|---|---|
| Что записать на полосу | **Только номер карты**, тот же, что заведён в Set10: дорожка 2 `;<номер>?` (ISO 7813, цифры). Дорожку 1 можно не писать. Шифровать нечего: полоса копируется любым ридером, защита — в привязке к телефону и в подтверждении списаний |
| Что ещё напечатать | Номер цифрами, **штрихкод Code128** с тем же номером (тогда хватит обычного сканера, считыватель полосы не обязателен), на обороте — **код активации** (4–6 цифр, лучше под скретч-слоем) |
| Как касса читает | Штатно: Set10 получает номер с полосы (`CardSearchEventSource.MAGNETIC_STRIPE`) так же, как со штрихкода — карта, «цена 3», плагин, начисление работают одинаково. **Проверить**: настройку маски/дорожки ридера в Set10 для типа карт |
| Первая покупка без привязки | Баллы копятся на «гостевом» счёте карты (сервер создаёт его сам при первом чеке) |
| Привязка к номеру телефона | Клиент в приложении: Профиль → «Привязать пластиковую карту» → номер + код активации → баллы переходят на его счёт. На кассе ничего не спрашиваем (без CardPlugin кассир не может открыть форму) |
| Загрузка | Админка → «Пул карт» → тип «пластиковые», строки `номер;код`. Коды хранятся только в виде HMAC |
| Списание с непривязанной карты | Запрещено (и в гипермаркете, и на 3 этаже) |

### Виртуальная и пластиковая карта у одного клиента

**Правило: на один телефон — не больше одной виртуальной и одной пластиковой карты; порядок появления любой.** Диапазоны номеров разделены: виртуальные (выдаются приложением) и пластиковые (печатаются) загружаются в пул разными типами, номер одного типа нельзя загрузить или привязать как другой. В Set10 обе карты — карты одного типа с «ценой 3», поэтому на кассе они работают одинаково; объединяет их наш сервер: **счёт и баланс один**.

| Сценарий | Что происходит |
|---|---|
| Только приложение | при регистрации выдаётся виртуальная карта, QR/штрихкод = её номер |
| Только пластик, без регистрации | баллы копятся на гостевом счёте карты; списывать нельзя |
| Пластик → потом регистрация → привязка | при регистрации выдаётся виртуальная; при привязке пластика гостевые баллы переходят на счёт; дальше обе карты копят на один счёт |
| Приложение → потом пластик | привязка пластика в профиле; гостевых баллов нет или они переносятся |
| Пластик уже привязан, клиент привязывает другой | отказ с вопросом «Заменить?»; при замене старая карта блокируется, баллы остаются |
| Пластик привязан к другому телефону | отказ |
| Свободных виртуальных номеров нет, а пластик привязан | в QR приложения показывается номер пластика (тоже карта Set10) |
| Утеря карты | клиент заменяет её в приложении или админ блокирует (админка → «Пул карт» → «Заблокировать карту») |
| Удаление аккаунта | виртуальная карта закрывается навсегда; пластик возвращается в свободные (у человека на руках) и начинает новый гостевой счёт |
| Обе карты в одном чеке | плагин берёт первую карту — начисление одно |

**QR и штрихкод не обновляются**: в них номер карты, а Set10 узнаёт только номера, заведённые в нём. Ежедневно меняющийся код потребовал бы CardPlugin (касса спрашивала бы наш сервер «чей это код»). Защита от передачи карты — не в QR, а в правилах: списание только у привязанной к телефону карты, в гипермаркете — по переключателю клиента, на 3 этаже — с кодом из приложения.

## 5. 3 этаж (кино, боулинг, другие кассы)

Без интеграции с их ПО: планшет/ПК с `/cashier` + **USB-сканер штрихкодов/QR** (работает как клавиатура) + при необходимости **USB-считыватель полосы** (тоже как клавиатура: страница кассира сама вырезает номер из `;номер=…?`). Подтверждение списания: у точки включается «Код подтверждения» — клиент видит 4-значный код в приложении и называет кассиру (без затрат на СМС). Интеграция с их ПО позже — через те же `/api/v1/redeem/*`.
