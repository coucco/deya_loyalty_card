# Внедрение: подключение касс гипермаркета к серверу лояльности

Порядок внедрения от пробного запуска до боевых касс. Сначала всё проверяется без касс, потом на одной тестовой кассе, и только потом везде.

## Этап 1. Сервер и приложение в работе

Выполните `docs/DEPLOY.md`. Результат: приложение открывается, вход по СМС работает, в админке есть ключ точки «Гипермаркет».

## Этап 2. Пробная проверка без касс (1 час)

1. Зарегистрируйтесь в приложении своим номером. В профиле посмотрите номер карты.
2. На `/cashier` с ключом гипермаркета «начислите» тестовый чек: баллы должны появиться в приложении.
3. Покажите QR на экране другому телефону/сканеру: должен считаться ваш 13-значный номер карты.

> **Актуальный пошаговый план с критериями — `docs/TEST_PLAN.md`; методы и плагины Set10 — `docs/SET10_PLUGINS.md`.**
> Ниже — исходная версия; этап 3 изменён: карты больше не генерируются сервером, а выдаются из пула номеров, заведённых в Set10.

## Этап 3. Карты приложения в Set Retail 10 (решено: пул карт)

Сервер в боевом режиме (`CARD_ISSUE_MODE=pool`) выдаёт клиенту при регистрации **свободный номер из пула**: номера заранее
создаются в Set10 как карты нужного типа (с «ценой 3») и загружаются в админку → «Пул карт» (списком или диапазоном).
Так касса узнаёт карту штатно, без CardPlugin. Пластиковые карты загружаются в тот же пул с типом «пластиковые» и кодом активации.
Ниже — прежние вопросы к Кристаллу; они остаются полезными для массового выпуска диапазонов.

Касса Set10 при сканировании должна опознать номер карты как карту лояльности; иначе плагин его не получит. **Здесь нужны данные от Кристалла/интегратора**, универсальной инструкции нет: открытой документации по загрузке внешних карт у меня нет.

Что подготовлено:

* Номера карт имеют префикс `2000` (настройка `CARD_PREFIX`) и контрольную цифру по Луну.
* Выгрузка всех карт: админка → «Клиенты» → «Выгрузить карты (CSV)», разделитель `;`, столбцы `card_number;phone;status`.

Вопросы к Кристаллу (скопируйте им):

1. Как загрузить в Set Retail 10 внешние номера карт (массово, по расписанию или по запросу)? Или можно настроить диапазон/маску номеров (`2000*`), чтобы любой номер с этим префиксом принимался как карта типа INTERNAL без предварительной загрузки?
2. Какая у нас версия Set Retail 10 и поддерживает ли она плагины лояльности (`LoyaltyPlugin`, API ≥ 0.0.46 для `onReceiptFiscalized`)?
3. Где в вашей версии регистрируется внешний процессинг и как доставляется jar на кассы?
4. Нужна ли «приёмка» плагина вашей стороной (чек-лист из SDK) перед боевым запуском?

Если Set10 не умеет принимать произвольные номера, остаётся путь «карты заводятся в Set10 заранее»: тогда нужна ежедневная выгрузка новых карт из нашей админки в Set10. Это ещё предстоит сделать после ответа Кристалла.

## Этап 4. Установка плагина на тестовую кассу

Полная инструкция с путями и настройками: `set10-bonus-plugin/README.md`. Коротко:

1. Впишите реальные контакты поставщика в `set10-bonus-plugin/gradle.properties` (`vendorEmail` или `vendorPhone`) и соберите: `gradle build` (готовый jar в `dist/` собран с **заглушкой** `CHANGE_ME@example.com` вместо контактов, а Set10 требует реальные; поэтому пересоберите после правки `gradle.properties`).
2. Скопируйте `DeyaBonusAccrualPlugin.jar` на сервер Set Retail и на **тестовую** кассу.
3. В Set10 «Интеграция → Внешние процессинги» зарегистрируйте плагин `ext.deya.bonus.accrual` и заполните настройки:

| Настройка | Значение |
|---|---|
| `server.url` | `https://<ваш домен>/api/v1/accruals` |
| `api.key` | ключ точки «Гипермаркет» из админки |
| `point.id` | `hypermarket` |
| `card.prefix` | `2000` (должен совпасть с `CARD_PREFIX`) |

4. Перезапустите кассовый модуль.

## Этап 5. Приёмочная проверка на тестовой кассе

Пройдите таблицу из 13 сценариев в `set10-bonus-plugin/README.md`. Минимум, без которого на боевые кассы нельзя:

| # | Сценарий | Ожидаемое |
|---|---|---|
| 1 | Чек с картой приложения | Через несколько секунд в приложении «+N баллов», в журнале сервера запись |
| 2 | Тот же чек повторно отправить (имитировать сбой связи: отключить сервер, пробить чек, включить) | Баллы начислены ровно один раз |
| 3 | Чек без карты | Ничего не отправляется, касса работает как раньше |
| 4 | Возврат по чеку с картой | Баллы уменьшились |
| 5 | Сервер выключен | Касса не тормозит и не выдаёт ошибок; после включения сервера чек доезжает |
| 6 | Скидки Set10 («цена 3») | Считаются как раньше; баллы начислены от суммы **после** скидок |
| 7 | Неверный `api.key` | Касса работает; в логе плагина понятная ошибка; после исправления ключа чек доезжает |

Сверьте ожидаемые баллы вручную: `сумма строк чека после скидок × процент ÷ 100`, округление по настройке.

## Этап 6. Боевой запуск

1. Задайте в админке **реальные проценты** (до этого гипермаркет начисляет 0 баллов, это защита от случайных начислений).
2. Установите плагин на остальные кассы, начните с одной, наблюдайте день.
3. Ежедневно первую неделю: блок «Расхождений журнала» в админке = 0, число начислений сопоставимо с числом чеков по картам в Set10.
4. Включите ежедневные копии БД (`DEPLOY.md`, раздел 4).

## Этап 7 (позже). Кино и боулинг

* **Быстрый путь без интеграции:** кассир кино/боулинга открывает `/cashier` на планшете/телефоне, вводит ключ своей точки, сканирует QR клиента (или вводит номер), видит «можно списать не больше N баллов», подтверждает. Скидку даёт вручную. Готово сейчас, нужны только проценты и ключи.
* **Автоматическая связка** с их ПО: нужно узнать у их разработчиков, есть ли плагины или API. Сервер к этому готов (`/api/v1/redeem/*`, `docs/API.md`): достаточно, чтобы их ПО умело HTTP-запросы «узнать лимит → зарезервировать → подтвердить/отменить».
